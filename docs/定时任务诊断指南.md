# 定时任务诊断指南

## 问题：定时任务部署到服务器后感觉没有执行

本文档提供详细的诊断步骤，帮助排查定时任务未执行的问题。

## 诊断步骤

### 1. 检查调度器状态

使用诊断API检查调度器是否正常运行：

```bash
# 获取调度器状态（需要管理员权限）
GET /api/v1/scheduled-tasks/scheduler-status
```

**返回信息包括：**
- `worker_pid`: 当前工作进程ID
- `scheduler_running`: 调度器是否正在运行（应为 `true`）
- `total_jobs`: 已注册的任务数量
- `jobs`: 任务详情列表（包含任务ID、名称、下次执行时间、触发器）

**预期结果：**
- `scheduler_running` 应为 `true`
- `total_jobs` 应大于 0（如果有启用的任务）
- 每个任务应有 `next_run_time`（下次执行时间）

### 2. 检查数据库中的任务配置

确保数据库中的任务配置正确：

```sql
-- 检查是否有启用的任务
SELECT id, task_name, cron_expression, is_active, function_path, description
FROM scheduled_tasks
WHERE is_active = TRUE;

-- 检查任务锁状态
SELECT task_name, is_running, last_run_time, locked_by_pid, locked_by_host
FROM task_locks;
```

**检查要点：**
1. **任务是否启用**：`is_active` 应为 `TRUE`
2. **Cron表达式是否设置**：`cron_expression` 不应为空
3. **函数路径是否正确**：`function_path` 应指向实际存在的函数
4. **任务锁状态**：`is_running` 不应长期为 `TRUE`（如果任务卡住）

### 3. 检查应用启动日志

查看应用启动时的日志，确认定时任务是否正确初始化：

```bash
# 查看日志文件
tail -f logs/app.log | grep -i "定时任务\|scheduler\|任务"
```

**关键日志信息：**
- `[Worker PID:xxx] 开始初始化定时任务...`
- `[Worker PID:xxx] 定时任务初始化完成: 成功注册 X 个任务, 跳过 Y 个任务`
- `[Worker PID:xxx] 定时任务调度器已启动，当前已注册 X 个任务`
- `[Worker PID:xxx] 已注册的任务列表:`（包含每个任务的详细信息）

**常见问题：**
- 如果看到 "数据库中没有启用的定时任务"，说明数据库中没有 `is_active=TRUE` 的任务
- 如果看到 "所有任务都被跳过"，检查任务函数路径是否正确
- 如果看到 "调度器已启动，但没有任何任务已注册"，说明任务注册失败

### 4. 检查任务执行日志

查看任务执行时的日志：

```bash
# 查看任务执行日志
tail -f logs/app.log | grep -i "定时任务执行\|任务.*开始执行\|任务.*执行完成"
```

**关键日志信息：**
- `[Worker PID:xxx] 任务 'xxx' 开始执行`
- `[定时任务执行] xxx 开始执行`
- `[定时任务执行] xxx 执行完成`

**如果看不到执行日志：**
- 检查任务的 `next_run_time` 是否已到
- 检查任务是否被其他进程锁定
- 检查进程分配逻辑（多进程环境下）

### 5. 检查任务队列状态

使用API检查任务队列状态：

```bash
# 获取任务队列状态
GET /api/v1/scheduled-tasks/queue-status
```

**返回信息包括：**
- `current_running`: 当前正在执行的任务数
- `max_concurrent`: 最大并发任务数（默认2）
- `queue_length`: 队列中等待的任务数
- `running_tasks`: 正在执行的任务名称列表
- `queued_tasks`: 队列中等待的任务名称列表

**如果任务在队列中等待：**
- 检查 `current_running` 是否已达到 `max_concurrent`
- 如果队列中有任务但 `current_running` 未满，可能是任务执行时间过长

### 6. 手动触发任务测试

使用API手动触发任务，测试任务函数是否正常：

```bash
# 手动触发任务
POST /api/v1/scheduled-tasks/{task_name}/trigger
```

**如果手动触发成功：**
- 说明任务函数本身没有问题
- 问题可能在于调度器配置或Cron表达式

**如果手动触发失败：**
- 检查任务函数是否有错误
- 查看错误日志了解具体原因

### 7. 检查多进程环境

如果使用多进程部署（如 Gunicorn + Uvicorn workers），注意：

1. **每个进程都有独立的调度器**：每个 worker 进程都会初始化自己的调度器
2. **进程分配机制**：相同执行时间的任务会被分配到不同的进程
3. **任务锁机制**：确保同一任务不会在多个进程中同时执行

**检查方法：**
- 查看日志中的 `[Worker PID:xxx]` 信息，确认不同进程都在运行
- 使用 `scheduler-status` API 检查不同进程的任务分配情况

### 8. 检查时区配置

确保应用时区配置正确：

```python
# app/core/config.py
TIMEZONE = "Asia/Shanghai"  # 或其他时区
```

**问题：**
- 如果时区配置错误，任务的执行时间可能与预期不符
- Cron表达式中的时间是基于配置的时区

### 9. 检查Cron表达式格式

确保Cron表达式格式正确（APScheduler 5字段格式）：

```
分 时 日 月 星期
* * * * *  # 每分钟执行
0 * * * *  # 每小时执行
0 0 * * *  # 每天执行
*/10 * * * *  # 每10分钟执行
```

**验证方法：**
- 使用 `/api/v1/scheduled-tasks/scheduler-status` 查看任务的 `trigger` 字段
- 使用 `/api/v1/scheduled-tasks/{task_name}` 查看任务的详细信息

## 常见问题及解决方案

### 问题1：调度器未启动

**症状：**
- `scheduler_running` 为 `false`
- 日志中没有 "定时任务调度器已启动" 的信息

**解决方案：**
1. 检查应用启动日志，查看是否有错误
2. 检查 `lifespan` 函数中的异常处理
3. 确保 `init_scheduled_tasks()` 和 `start_scheduler()` 被正确调用

### 问题2：任务未注册

**症状：**
- `total_jobs` 为 0
- 日志显示 "调度器已启动，但没有任何任务已注册"

**解决方案：**
1. 检查数据库中的任务配置（`is_active=TRUE`）
2. 检查任务函数路径是否正确
3. 检查 `function_path` 是否指向实际存在的函数
4. 查看日志中的 "跳过" 信息，了解具体原因

### 问题3：任务已注册但未执行

**症状：**
- `total_jobs` 大于 0
- `next_run_time` 已过，但任务未执行
- 没有看到任务执行日志

**解决方案：**
1. 检查任务锁状态（可能被其他进程锁定）
2. 检查进程分配逻辑（多进程环境下）
3. 检查任务队列是否已满
4. 查看是否有错误日志

### 问题4：任务执行失败

**症状：**
- 看到 "任务开始执行" 日志
- 但没有看到 "任务执行完成" 日志
- 或者看到错误日志

**解决方案：**
1. 查看详细的错误日志
2. 检查任务函数中的异常处理
3. 手动触发任务测试，查看具体错误信息

### 问题5：多进程环境下任务重复执行

**症状：**
- 同一任务在多个进程中同时执行
- 日志中出现重复的执行记录

**解决方案：**
1. 检查任务锁机制是否正常工作
2. 检查数据库连接是否正常
3. 检查 `task_locks` 表的状态

## 诊断工具

### 1. 调度器状态API

```bash
GET /api/v1/scheduled-tasks/scheduler-status
```

### 2. 任务队列状态API

```bash
GET /api/v1/scheduled-tasks/queue-status
```

### 3. 任务列表API

```bash
GET /api/v1/scheduled-tasks/
```

### 4. 手动触发任务API

```bash
POST /api/v1/scheduled-tasks/{task_name}/trigger
```

## 日志位置

- **应用日志**：`logs/app.log`
- **日志格式**：包含进程ID（`[Worker PID:xxx]`）和时间戳
