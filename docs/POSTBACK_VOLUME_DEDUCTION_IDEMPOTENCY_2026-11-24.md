# Postback 被扣量事件幂等性修复说明

**日期：** 2026-11-24  
**状态：** PR 验证中，尚未合并

## 问题

Postback 的重复检测原本只查询 `postback_conversions`。命中 volume deduction 时，业务会写入 `conversion_deduction_logs` 后跳过正式转化入库，因此同一 `platform + conversion_id + event_name` 的后续重试无法在正式转化表中找到原事件。

扣量日志当前没有保存完整事件身份，不能安全地用 `click_id` 替代：一个 click 可能对应多个合法转化事件。

## 修复设计

新增 `postback_event_receipts`，使用与正式转化表相同的复合唯一身份：

`platform + conversion_id + normalized event_name`

1. 重复检测先查询历史正式转化。
2. 未找到时，在当前数据库事务内通过 savepoint 插入唯一收据。唯一键冲突表示事件已被另一事务处理或预留。
3. 插入收据后再次查询正式转化，封闭“并发请求等待普通转化事务释放临时收据”的竞态。
4. 命中扣量并跳过正式转化入库时，收据与扣量日志一起提交并长期保留。
5. 正常转化成功写入 `postback_conversions` 后，在同一事务删除临时收据。正式转化表的唯一约束继续承担长期幂等。
6. 任意业务事务回滚时，收据自动回滚，不留下错误的“已处理”标记。

## 并发语义

- 两个相同事件并发到达时，数据库唯一索引负责仲裁；第二个请求等待第一个事务结束。
- 第一个请求提交扣量收据后，第二个请求命中收据唯一冲突并返回重复。
- 第一个请求提交正式转化并删除临时收据后，第二个请求可能插入自己的临时收据，但二次查询会看到正式转化，删除自己的收据并返回重复。
- 第一个请求回滚时，第二个请求可以成功取得收据并正常处理。

不依赖 Redis 锁，因此 Redis 重启不会丢失该幂等凭证。

## 历史数据边界

历史 volume-deducted 日志没有 `platform`、`conversion_id`、`event_name` 字段，无法可靠回填这些收据。新机制只对部署后进入的新事件提供完整保证；部署前已扣量且没有正式转化记录的事件，不能声称可以被历史回填自动识别。

## 部署切换要求

该机制需要新旧 Postback 处理代码同时认识收据表。旧版本不会创建或读取收据，因此不能在旧、新 Postback Worker 长时间混跑时宣称完整幂等。

上线时应采用蓝绿切换或短暂停收/排空方式：
1. 先执行数据库迁移，创建收据表。
2. 暂停或摘除旧版本 Postback 接入流量，等待旧 Worker 的在途事务结束。
3. 部署并启动包含收据逻辑的新版本 Worker。
4. 确认所有 Postback Worker 都已升级后，再恢复入口流量。
5. 验证重复扣量回调、正常转化并发回调和 Redis 不可用场景。

不得只滚动替换部分 Worker 后就恢复全量流量。

## 运维与保留策略

- 收据表只长期保留未入库的 volume-deducted 事件；正常转化的临时收据在正式记录保存后同事务删除。
- 不设置未经业务确认的自动过期任务。删除扣量收据会重新打开旧事件重放窗口；未来如需清理，必须先明确上游最大重试周期和财务对账保留期。
- 数据库迁移通过显式 manifest 和 SHA-256 校验管理。
- 不使用 Redis 锁、进程内锁或 TTL 代替数据库唯一约束。
