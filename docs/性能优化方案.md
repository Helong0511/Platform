# 性能优化方案 - 2核4G内存服务器

## 优化目标
针对2核CPU + 4GB内存的服务器，优化短链接和CPL服务的高并发性能。

## 已实施的优化

### 1. 短链接服务优化 ⭐⭐⭐

#### 1.1 Redis缓存机制
- **问题**：每次重定向都要查询数据库，高并发时数据库压力大
- **解决方案**：
  - 使用Redis缓存短链接数据（TTL: 1小时）
  - 缓存命中时直接重定向，无需查询数据库
  - 缓存未命中时查询数据库并写入缓存
- **性能提升**：缓存命中率>90%时，数据库查询减少90%以上

#### 1.2 异步点击次数更新
- **问题**：同步更新点击次数会阻塞重定向，影响响应速度
- **解决方案**：
  - 使用Redis原子计数器异步记录点击次数
  - 定时任务每5分钟批量同步到数据库
  - 重定向不再等待数据库更新
- **性能提升**：重定向响应时间减少50-80ms

#### 1.3 代码位置
- `app/core/short_link_cache.py` - 短链接缓存模块
- `app/core/short_link_click_counter.py` - 点击次数异步更新模块
- `app/scheduler/short_link_tasks.py` - 定时同步任务
- `app/main.py` - 优化后的重定向接口

### 2. Redis连接池优化 ⭐⭐

#### 2.1 连接池配置
- **问题**：单例Redis连接在高并发时成为瓶颈
- **解决方案**：
  - 启用Redis连接池（max_connections: 20）
  - 启用TCP keepalive保持连接
  - 优化连接超时和重试机制
- **性能提升**：支持更高并发，减少连接建立开销

#### 2.2 代码位置
- `app/core/redis_client.py` - Redis客户端优化

### 3. 数据库连接池优化 ⭐

#### 3.1 连接数调整
- **问题**：连接数过多会占用内存
- **解决方案**：
  - 每个worker: pool_size=12, max_overflow=8（原15+10）
  - 3个workers总连接数：60（原75）
  - 节省内存约15-20MB
- **性能影响**：短链接服务主要使用缓存，数据库压力小，连接数足够

#### 3.2 代码位置
- `app/core/config.py` - 数据库连接池配置

### 4. Gunicorn配置优化 ⭐⭐

#### 4.1 Worker配置
- **workers**: 3（2核CPU，保持不变）
- **worker_connections**: 1000（Uvicorn默认，支持高并发）
- **max_requests**: 1000（原500，提高以支持高并发）
- **timeout**: 60秒（原120秒，短链接重定向应该很快）
- **keepalive**: 10秒（原5秒，增加连接复用）

#### 4.2 性能提升
- 支持约3000并发连接（3 workers × 1000 connections）
- 减少超时等待，提高响应速度
- 更好的连接复用，减少连接建立开销

#### 4.3 代码位置
- `gunicorn.conf.py` - Gunicorn配置优化

### 5. 日志优化 ⭐

#### 5.1 减少高并发日志
- **问题**：每次请求都记录日志，高并发时I/O压力大
- **解决方案**：
  - 短链接重定向接口移除详细日志（保留错误日志）
  - 使用logger.debug替代logger.info（生产环境不输出）
- **性能提升**：减少I/O操作，提高响应速度

## 性能指标预期

### 短链接服务
- **缓存命中率**: >90%（热数据）
- **响应时间**: 
  - 缓存命中: <10ms
  - 缓存未命中: <50ms
- **并发能力**: 3000+ QPS（3 workers × 1000 connections）
- **数据库压力**: 减少90%以上（缓存命中时）

### CPL服务
- **Redis计数器**: 原子操作，延迟<5ms
- **数据库同步**: 批量更新，每5分钟一次
- **并发能力**: 支持高并发Cap检查

### 服务器资源
- **内存使用**: 
  - 每个worker: ~200-300MB
  - 3个workers: ~600-900MB
  - Redis缓存: ~100-200MB
  - 系统和其他: ~500MB
  - **总计**: ~1.2-1.6GB（4GB内存充足）
- **CPU使用**: 
  - 正常负载: 30-50%
  - 高并发: 60-80%
  - 峰值: <90%

## 进一步优化建议

### 1. 如果Redis内存不足
- 减少缓存TTL（如30分钟）
- 使用LRU淘汰策略
- 考虑Redis集群

### 2. 如果数据库压力仍然大
- 增加数据库连接池（如果内存允许）
- 考虑读写分离
- 使用数据库连接池监控

### 3. 如果CPU使用率过高
- 考虑增加服务器配置
- 优化代码逻辑
- 使用CDN加速静态资源

### 4. 如果内存不足
- 减少worker数量（如改为2个）
- 减少数据库连接池大小
- 优化应用代码，减少内存占用

## 注意事项

1. **Redis必须运行**：短链接缓存和点击计数依赖Redis，如果Redis不可用会降级到数据库查询
2. **定时任务必须运行**：点击次数需要定时同步到数据库，确保定时任务系统正常运行
3. **监控缓存命中率**：如果缓存命中率低，检查Redis配置和TTL设置
4. **定期检查Redis内存**：如果Redis内存不足，考虑增加内存或优化缓存策略

## 回滚方案

如果优化后出现问题，可以：
1. 恢复Gunicorn配置（`gunicorn.conf.py`）
2. 恢复数据库连接池配置（`app/core/config.py`）
3. 短链接服务会自动降级到数据库查询（如果Redis不可用）
