# 渠道配置功能详细说明

## 一、功能概述

渠道配置是CPL系统中用于管理Offer与渠道（Publisher）关联关系的核心功能。通过渠道配置，可以为每个Offer的每个渠道单独设置**下游PO**（扣价后支付金额）和**下游Cap**（转化上限）。

### 1.1 界面位置

- **位置：** Offer管理页面 → 创建/编辑Offer → "分配渠道"部分
- **界面元素：**
  - 渠道配置卡片（可添加多个）
  - 选择渠道下拉框（必填）
  - 下游PO输入框（可选）
  - 下游Cap输入框（可选）

### 1.2 数据存储

**数据表：** `offer_publisher_assignments`

**字段说明：**
- `offer_id`: Offer ID（外键）
- `publisher_id`: 渠道ID（外键）
- `downstream_cap`: 该渠道的下游转化上限（整数，可选）
- `affiliate_payout`: 该渠道的扣价后给渠道的金额（浮点数，可选）
- `is_active`: 是否激活（布尔值，默认true）
- `created_at`: 创建时间
- `updated_at`: 更新时间

**唯一约束：** `(offer_id, publisher_id)` - 确保每个Offer的每个渠道只有一条配置记录

## 二、字段详细说明

### 2.1 下游PO（affiliate_payout）

**字段名：** `affiliate_payout`  
**类型：** `Float`（浮点数）  
**单位：** 货币单位（如美元、人民币等）  
**精度：** 2位小数  
**最小值：** 0（不能为负数）

**含义：**
- **该渠道的扣价后支付金额**
- 这是经过CPL系统扣量计算后，实际支付给渠道的金额
- 与 `conversion.payout`（扣减后的金额）不同，`affiliate_payout` 是**针对特定渠道的固定金额**

**使用场景：**
1. **转化转发时**：转发给渠道的 `payout` 字段可以使用 `affiliate_payout`（如果配置了）
2. **统计报表**：用于计算该渠道的实际收益
3. **对账结算**：作为支付给渠道的依据

**示例：**
- 原始转化金额：`2.80`
- 系统扣减后金额：`2.24`（扣减20%）
- 渠道配置的下游PO：`0.10`（固定金额）
- 转发给渠道的金额：使用 `affiliate_payout`（`0.10`）而不是 `conversion.payout`（`2.24`）

**注意：**
- 如果未配置 `affiliate_payout`，转发时使用 `conversion.payout`（扣减后的金额）
- `affiliate_payout` 是**固定金额**，不会根据转化金额动态计算
- 可以为不同渠道设置不同的 `affiliate_payout`，实现差异化定价

### 2.2 下游Cap（downstream_cap）

**字段名：** `downstream_cap`  
**类型：** `Integer`（整数）  
**单位：** 转化次数  
**最小值：** 0（不能为负数）

**含义：**
- **该渠道的转化上限**
- 限制该渠道在指定Offer上的最大转化数量
- 与Offer级别的 `upstream_cap`（上游Cap）不同，`downstream_cap` 是**针对特定渠道的限制**

**使用场景：**
1. **转化限制**：当该渠道的转化数量达到 `downstream_cap` 时，不再接受新的转化
2. **流量分配**：可以给不同渠道设置不同的Cap，实现流量分配策略
3. **风险控制**：限制单个渠道的转化数量，降低风险

**示例：**
- Offer的上游Cap：`1000`（整个Offer的转化上限）
- 渠道A的下游Cap：`500`（渠道A最多500个转化）
- 渠道B的下游Cap：`300`（渠道B最多300个转化）
- 渠道C的下游Cap：`200`（渠道C最多200个转化）

**注意：**
- 如果未配置 `downstream_cap`，不限制该渠道的转化数量（但仍受Offer级别的 `upstream_cap` 限制）
- `downstream_cap` 是**渠道级别的限制**，与Offer级别的Cap是独立的
- 所有渠道的 `downstream_cap` 总和可以超过Offer的 `upstream_cap`（因为不同渠道可能不会同时达到上限）

## 三、业务流程

### 3.1 创建Offer时的渠道配置

```
1. 创建Offer
   ↓
2. 在"分配渠道"部分添加渠道配置
   - 选择渠道（必填）
   - 设置下游PO（可选）
   - 设置下游Cap（可选）
   ↓
3. 保存Offer
   ↓
4. 系统创建 OfferPublisherAssignment 记录
   - offer_id: 新创建的Offer ID
   - publisher_id: 选择的渠道ID
   - affiliate_payout: 设置的下游PO（如果有）
   - downstream_cap: 设置的下游Cap（如果有）
   - is_active: true
```

### 3.2 转化处理时的使用

#### 场景1：使用affiliate_payout作为转发金额

**当前实现：**
- 转化转发时，`_build_forward_data()` 函数使用 `conversion.payout`（扣减后的金额）
- **未使用** `affiliate_payout` 字段

**建议优化：**
- 如果配置了 `affiliate_payout`，优先使用 `affiliate_payout` 作为转发金额
- 如果未配置，使用 `conversion.payout`（扣减后的金额）

**代码位置：** `app/core/postback/forwarder.py:561-647`

#### 场景2：使用downstream_cap限制转化

**当前实现：**
- Cap检查在 `app/core/cap/cap_manager.py` 中实现
- 主要检查Offer级别的Cap（`upstream_cap`）
- **未检查**渠道级别的Cap（`downstream_cap`）

**建议优化：**
- 在Cap检查时，同时检查 `downstream_cap`
- 如果该渠道的转化数量已达到 `downstream_cap`，拒绝转化

**代码位置：** `app/core/postback/processor.py:365-372`

### 3.3 短链接与渠道配置的关联

**关联路径：**
```
短链接点击
    ↓
创建Click记录（包含 offer_id, publisher_id）
    ↓
转化回调
    ↓
查找 OfferPublisherAssignment（通过 offer_id + publisher_id）
    ↓
获取 affiliate_payout 和 downstream_cap
    ↓
应用Cap检查（使用 downstream_cap）
    ↓
转发转化（使用 affiliate_payout 或 conversion.payout）
```

## 四、与CPL系统的关联

### 4.1 扣量逻辑

**当前扣量流程：**
1. 接收转化回调（原始金额：`2.80`）
2. 应用扣量逻辑（扣减后金额：`2.24`）
3. 保存到 `conversion.payout` 字段
4. 转发给渠道时使用 `conversion.payout`

**使用affiliate_payout的流程：**
1. 接收转化回调（原始金额：`2.80`）
2. 应用扣量逻辑（扣减后金额：`2.24`）
3. 保存到 `conversion.payout` 字段
4. **查找 OfferPublisherAssignment，获取 `affiliate_payout`**
5. **如果配置了 `affiliate_payout`，使用 `affiliate_payout` 作为转发金额**
6. 如果未配置，使用 `conversion.payout`

### 4.2 Cap检查逻辑

**当前Cap检查：**
- 只检查Offer级别的Cap（`offers.upstream_cap`）
- 不检查渠道级别的Cap（`offer_publisher_assignments.downstream_cap`）

**建议的Cap检查：**
1. 检查Offer级别的Cap（`offers.upstream_cap`）
2. **检查渠道级别的Cap（`offer_publisher_assignments.downstream_cap`）**
3. 如果任一Cap超限，拒绝转化

### 4.3 转化转发逻辑

**当前转发逻辑：**
```python
# app/core/postback/forwarder.py:585-590
if conversion.payout is not None:
    data["payout"] = conversion.payout
elif conversion.original_payout is not None:
    data["payout"] = conversion.original_payout
```

**建议的转发逻辑：**
```python
# 优先使用 affiliate_payout（如果配置了）
assignment = await db.execute(
    select(OfferPublisherAssignment).where(
        OfferPublisherAssignment.offer_id == conversion.offer_id,
        OfferPublisherAssignment.publisher_id == conversion.publisher_id,
        OfferPublisherAssignment.is_active == True
    )
)
if assignment and assignment.affiliate_payout is not None:
    data["payout"] = assignment.affiliate_payout
elif conversion.payout is not None:
    data["payout"] = conversion.payout
elif conversion.original_payout is not None:
    data["payout"] = conversion.original_payout
```

## 五、数据模型关系

### 5.1 表关系图

```
Offer (offers)
    ↓ (一对多)
OfferPublisherAssignment (offer_publisher_assignments)
    ↓ (多对一)
Publisher (publishers)

关系说明：
- 一个Offer可以有多个渠道配置（一个Offer可以分配给多个渠道）
- 一个渠道可以有多个Offer配置（一个渠道可以接收多个Offer）
- 每个 (offer_id, publisher_id) 组合只有一条配置记录（唯一约束）
```

### 5.2 关键字段对比

| 字段 | 表 | 含义 | 使用场景 |
|------|-----|------|----------|
| `payout` | `offers` | 上游支付金额（原始金额） | Offer级别的原始金额 |
| `affiliate_payout` | `offers` | Offer级别的扣价后金额（旧字段，已废弃） | 不再使用 |
| `affiliate_payout` | `offer_publisher_assignments` | **渠道级别的扣价后金额** | **转化转发时使用** |
| `payout` | `postback_conversions` | 扣减后的金额（`conversion.payout`） | 系统扣量后的金额 |
| `original_payout` | `postback_conversions` | 原始金额（`conversion.original_payout`） | 转化回调的原始金额 |

## 六、配置示例

### 6.1 场景示例

**Offer信息：**
- Offer ID: `11`
- Offer名称: `测试Offer`
- 上游PO: `2.80`
- 上游Cap: `1000`

**渠道配置：**

| 渠道ID | 渠道名称 | 下游PO | 下游Cap | 说明 |
|--------|----------|--------|---------|------|
| 4 | Test渠道 | `0.10` | `1` | 固定金额0.10，最多1个转化 |
| 5 | 渠道A | `2.00` | `500` | 固定金额2.00，最多500个转化 |
| 6 | 渠道B | `1.50` | `300` | 固定金额1.50，最多300个转化 |

### 6.2 转化处理示例

**场景：渠道4（Test渠道）产生转化**

1. **接收转化回调：**
   - 原始金额：`2.80`
   - click_id: `0123456789AbCdEf`（系统生成的）

2. **应用扣量逻辑：**
   - 扣减后金额：`2.24`（假设扣减20%）
   - 保存到 `conversion.payout = 2.24`

3. **查找渠道配置：**
   ```sql
   SELECT * FROM offer_publisher_assignments
   WHERE offer_id = 11 AND publisher_id = 4 AND is_active = 1
   ```
   - 结果：`affiliate_payout = 0.10`, `downstream_cap = 1`

4. **检查Cap限制：**
   - 检查Offer级别的Cap：`upstream_cap = 1000`（未超限）
   - **检查渠道级别的Cap：`downstream_cap = 1`**
     - 查询该渠道已转化数量：`SELECT COUNT(*) FROM postback_conversions WHERE ...`
     - 如果已转化数量 >= 1，拒绝转化
     - 如果已转化数量 < 1，允许转化

5. **转发转化数据：**
   - 使用 `affiliate_payout = 0.10` 作为转发金额（而不是 `conversion.payout = 2.24`）
   - 转发数据：
     ```json
     {
       "click_id": "wnDYcdbppM3dBkeNAtf4ncebHzEhz8TM",
       "sub_channel_id": "1000",
       "payout": 0.10
     }
     ```

### 8.2 Cap检查优化

**文件：** `app/core/cap/cap_manager.py`

**函数：** `check_cap()`

**当前实现：**
- 只检查 `OfferCap` 表的Cap（`offer_caps` 表）
- `OfferCap` 表支持Publisher级别的Cap（`publisher_id` 字段）
- **未检查** `OfferPublisherAssignment.downstream_cap`（渠道配置的Cap）

**两个Cap系统的区别：**

| Cap类型 | 表名 | 字段 | 用途 | 配置位置 |
|---------|------|------|------|----------|
| **Cap配置** | `offer_caps` | `daily_cap`, `total_cap` | 通用的Cap限制配置 | Cap管理页面 |
| **渠道配置Cap** | `offer_publisher_assignments` | `downstream_cap` | 渠道在特定Offer上的转化上限 | Offer管理 → 分配渠道 |

**修改建议：**
```python
# 在检查OfferCap后，检查渠道配置的downstream_cap
if publisher_id:
    # 1. 先检查OfferCap（现有逻辑）
    # ... 现有代码 ...
    
    # 2. 再检查渠道配置的downstream_cap（新增）
    assignment_result = await db.execute(
        select(OfferPublisherAssignment).where(
            OfferPublisherAssignment.offer_id == offer_id,
            OfferPublisherAssignment.publisher_id == publisher_id,
            OfferPublisherAssignment.is_active == True
        )
    )
    assignment = assignment_result.scalars().first()
    
    if assignment and assignment.downstream_cap is not None:
        # 查询该渠道在该Offer上的已转化数量
        conversion_count_query = select(func.count(PostbackConversion.id)).join(
            ClickStats, PostbackConversion.click_id == ClickStats.click_id
        ).where(
            and_(
                ClickStats.offer_id == offer_id,
                ClickStats.publisher_id == publisher_id,
                PostbackConversion.conversion_status.in_(['Pending', 'Approved'])
            )
        )
        conversion_count_result = await db.execute(conversion_count_query)
        current_count = conversion_count_result.scalar() or 0
        
        if current_count >= assignment.downstream_cap:
            return False, f"渠道配置的Cap超限: {current_count}/{assignment.downstream_cap}"
```

## 九、Cap系统对比说明

### 9.1 两个Cap系统的关系

系统中有**两个独立的Cap系统**，它们有不同的用途：

#### Cap配置系统（OfferCap表）

**表名：** `offer_caps`  
**用途：** 通用的Cap限制配置  
**配置位置：** Cap管理页面  
**特点：**
- 支持Offer级别和Publisher级别的Cap
- 支持每日Cap（`daily_cap`）和总Cap（`total_cap`）
- 有计数功能（`current_daily_count`, `current_total_count`）
- 支持Redis缓存优化

**使用场景：**
- 限制整个Offer的转化数量
- 限制特定渠道在所有Offer上的转化数量
- 需要计数和自动重置的场景

#### 渠道配置Cap系统（OfferPublisherAssignment.downstream_cap）

**表名：** `offer_publisher_assignments`  
**字段：** `downstream_cap`  
**用途：** 渠道在特定Offer上的转化上限  
**配置位置：** Offer管理 → 分配渠道  
**特点：**
- 只针对特定Offer的特定渠道
- 简单的整数上限，无计数功能
- 与 `affiliate_payout` 一起配置

**使用场景：**
- 限制单个渠道在特定Offer上的转化数量
- 实现流量分配策略
- 风险控制（限制单个渠道的转化）

### 9.2 优先级关系

**建议的检查顺序：**
1. **先检查OfferCap**（通用Cap配置）
2. **再检查downstream_cap**（渠道配置Cap）
3. 如果任一Cap超限，拒绝转化

**示例：**
```
OfferCap配置：
- Offer 11 的 daily_cap = 1000（整个Offer的每日上限）

渠道配置：
- 渠道4在Offer 11上的 downstream_cap = 1（该渠道最多1个转化）

检查流程：
1. 检查Offer 11的每日Cap：当前转化数 < 1000，通过
2. 检查渠道4在Offer 11上的Cap：当前转化数 >= 1，拒绝
```

## 十、总结

### 10.1 功能特点

1. **渠道级别的独立配置**：每个渠道可以设置不同的下游PO和下游Cap
2. **固定金额定价**：`affiliate_payout` 是固定金额，不随转化金额变化
3. **流量分配控制**：通过 `downstream_cap` 控制每个渠道的转化上限
4. **灵活配置**：下游PO和下游Cap都是可选的，可以根据需要配置

### 10.2 业务价值

1. **差异化定价**：不同渠道可以设置不同的支付金额
2. **风险控制**：通过Cap限制控制单个渠道的转化数量
3. **流量分配**：合理分配流量到不同渠道
4. **对账结算**：使用固定的 `affiliate_payout` 便于对账

### 10.3 待优化项

1. **转化转发时使用 affiliate_payout**（高优先级）
2. **Cap检查时使用 downstream_cap**（高优先级）
3. **统计报表中显示渠道配置信息**（中优先级）
4. **批量导入/导出渠道配置**（低优先级）
