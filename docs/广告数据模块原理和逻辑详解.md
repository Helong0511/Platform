## 一、概述

广告数据模块是平台的核心业务模块，用于存储、查询和管理广告效果数据。数据包括请求数、匹配数、展示数、点击数、eCPM和收益等关键指标。

### 核心特性
- **多数据源支持**：支持从TQT API自动获取和Excel手动导入
- **数据去重**：确保同一日期和产品只有一条记录
- **自动计算**：自动计算覆盖率、展示率、点击率和减扣后的值
- **权限隔离**：客户只能查看自己的数据，管理员可查看所有数据
- **产品分配历史**：支持产品在不同客户间转移，历史数据归属正确

## 二、数据模型

### 2.1 表结构（ad_data）

```sql
CREATE TABLE `ad_data` (
    `id` INT PRIMARY KEY AUTO_INCREMENT COMMENT '广告数据ID',
    `date` DATETIME NOT NULL COMMENT '数据日期',
    `product_id` INT NOT NULL COMMENT '产品ID',
    `request_count` INT DEFAULT 0 COMMENT '请求数',
    `match_count` INT DEFAULT 0 COMMENT '匹配数',
    `display_count` INT DEFAULT 0 COMMENT '展示数',
    `click_count` INT DEFAULT 0 COMMENT '点击数',
    `ecpm_before_deduct` FLOAT DEFAULT 0.0 COMMENT 'eCPM未减扣',
    `ecpm_after_deduct` FLOAT DEFAULT 0.0 COMMENT 'eCPM已减扣',
    `revenue_before_deduct` FLOAT DEFAULT 0.0 COMMENT '收益未减扣',
    `revenue_after_deduct` FLOAT DEFAULT 0.0 COMMENT '收益已减扣',
    `coverage_rate` FLOAT GENERATED ALWAYS AS (...) STORED COMMENT '覆盖率',
    `display_rate` FLOAT GENERATED ALWAYS AS (...) STORED COMMENT '展示率',
    `click_rate` FLOAT GENERATED ALWAYS AS (...) STORED COMMENT '点击率',
    `created_at` DATETIME(6) DEFAULT CURRENT_TIMESTAMP(6),
    `updated_at` DATETIME(6) DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
    UNIQUE KEY `uq_ad_data_date_product` (`date`, `product_id`),
    INDEX `idx_ad_data_date` (`date`),
    INDEX `idx_ad_data_product` (`product_id`),
    INDEX `idx_ad_data_date_product` (`date`, `product_id`)
);
```

### 2.2 字段说明

#### 基础字段
- **id**: 主键，自增
- **date**: 数据日期（DateTime类型，存储为系统时区的naive datetime）
- **product_id**: 产品ID（外键关联products表）

#### 指标字段
- **request_count**: 请求数 - 广告请求的总次数
- **match_count**: 匹配数 - 成功匹配的请求数
- **display_count**: 展示数 - 实际展示的广告数
- **click_count**: 点击数 - 用户点击的广告数

#### 收益字段
- **ecpm_before_deduct**: eCPM未减扣 - 每千次展示的收益（减扣前）
- **ecpm_after_deduct**: eCPM已减扣 - 每千次展示的收益（减扣后）
- **revenue_before_deduct**: 收益未减扣 - 总收益（减扣前）
- **revenue_after_deduct**: 收益已减扣 - 总收益（减扣后）

#### 计算字段（数据库生成列）
- **coverage_rate**: 覆盖率 = (匹配数 / 请求数) × 100
- **display_rate**: 展示率 = (展示数 / 匹配数) × 100
- **click_rate**: 点击率 = (点击数 / 展示数) × 100

### 2.3 唯一性约束

**唯一约束**: `(date, product_id)`
- 确保同一日期和产品只能有一条记录
- 防止数据重复
- 更新时使用 `ON DUPLICATE KEY UPDATE` 或先查询后更新

### 2.4 索引设计

1. **idx_ad_data_date**: 优化日期范围查询
2. **idx_ad_data_product**: 优化产品查询
3. **idx_ad_data_date_product**: 复合索引，优化最常见的查询模式（日期+产品）

## 三、数据来源

### 3.1 TQT API自动获取

**位置**: `app/scheduler_module/tasks/tqt_task.py`

#### 工作流程
```
1. 定时任务触发（每30分钟）
   ↓
2. 构建API请求参数
   - appKey: 应用密钥
   - startDate: 系统时区的昨天
   - endDate: 系统时区的今天
   - page: 页码（从1开始）
   - pageSize: 100条/页
   - type: "all"
   ↓
3. 生成MD5签名
   - 按参数名排序
   - 拼接为字符串
   - MD5加密
   ↓
4. 调用TQT API
   - URL: https://union.e-kivi.com/open/api/report/data
   - 方法: POST
   - 格式: JSON
   ↓
5. 解析响应数据
   - 检查state='ok'或code=200
   - 提取data.list或list数组
   ↓
6. 遍历处理每条数据
   - 验证日期格式
   - 验证产品名称
   - 查找/创建产品
   - 检查重复
   - 计算减扣值
   - 插入/更新数据库
   ↓
7. 提交事务
   ↓
8. 记录统计信息
```

#### 关键逻辑

**日期处理**:
- TQT API返回的日期是系统时区（Asia/Shanghai）
- 直接解析为naive datetime，不转换时区
- 格式：`YYYY-MM-DD`

**产品匹配**:
- 使用`url`字段作为产品名称（优先）
- 如果`url`为空，使用`show_name`字段
- 通过产品名称查找产品，找不到则创建新产品

**数据去重**:
- 检查数据库中是否已存在相同`(date, product_id)`的记录
- 如果存在，更新现有记录
- 如果不存在，插入新记录

### 5.1 默认行为

**默认日期范围**: 当前月（本月1日到本月最后一日）

**默认排序**: 按日期降序（最新的在前）

**默认分页**: 
- 桌面端：10条/页
- 平板端：15条/页
- 手机端：10条/页

### 5.2 筛选条件

#### 5.2.1 日期范围筛选

**逻辑**:
- 如果指定了`start_date`和`end_date`，使用指定范围
- 如果未指定，默认使用当前月
- 日期比较：`AdData.date >= start_datetime AND AdData.date <= end_datetime`

**实现**:
```python

    query = query.where(AdData.date <= end_datetime)
elif not start_date and not end_date:

    month_start = date(today.year, today.month, 1)
    _, last_day = monthrange(today.year, today.month)
    month_end = date(today.year, today.month, last_day)

    query = query.where(AdData.date <= month_end_datetime)
```

## 六、权限控制

### 6.1 数据隔离机制

#### 管理员（ADMIN）
- **权限**: 可查看所有客户的广告数据
- **筛选**: 可按客户ID筛选，查看特定客户的数据
- **操作**: 可创建、修改、删除任意数据

#### 客户（CLIENT）
- **权限**: 只能查看自己的广告数据
- **筛选**: 自动过滤为自己的数据，无法查看其他客户的数据
- **操作**: 只能查看，不能修改或删除

### 6.2 权限过滤实现

**查询时权限过滤**:
```python
if current_user.role != UserRole.ADMIN:
    # 客户用户：通过Client.user_id过滤
    query = query.where(Client.user_id == current_user.id)
else:
    # 管理员：可按客户ID过滤（可选）
    if client_id:
        query = query.where(Client.id == client_id)
```

**产品列表权限过滤**:
```python
if current_user.role != UserRole.ADMIN:
    # 客户用户：只返回自己的产品
    query = query.where(Client.user_id == current_user.id)
elif client_id:
    # 管理员按客户ID过滤
    query = query.where(Client.id == client_id)
```

## 七、计算字段

### 7.1 覆盖率（coverage_rate）

**公式**: `覆盖率 = (匹配数 / 请求数) × 100`

**说明**: 
- 表示请求中成功匹配的比例
- 范围：0-100%
- 如果请求数为0，返回0

**实现**:
```python
@property
def coverage_rate(self) -> float:
    return round(self.match_count / self.request_count * 100 
                 if self.request_count > 0 else 0, 2)
```

### 7.2 展示率（display_rate）

**公式**: `展示率 = (展示数 / 匹配数) × 100`

**说明**:
- 表示匹配中实际展示的比例
- 范围：0-100%
- 如果匹配数为0，返回0

**实现**:
```python
@property
def display_rate(self) -> float:
    return round(self.display_count / self.match_count * 100 
                 if self.match_count > 0 else 0, 2)
```

### 7.3 点击率（click_rate）

**公式**: `点击率 = (点击数 / 展示数) × 100`

**说明**:
- 表示展示中用户点击的比例
- 范围：0-100%
- 如果展示数为0，返回0

**实现**:
```python
@property
def click_rate(self) -> float:
    return round(self.click_count / self.display_count * 100 
                 if self.display_count > 0 else 0, 2)
```

### 7.4 数据库生成列

在数据库中，这些计算字段被定义为**生成列（GENERATED COLUMN）**，自动计算并存储：

```sql
`coverage_rate` FLOAT GENERATED ALWAYS AS (
    CASE 
        WHEN `request_count` > 0 
        THEN ROUND(`match_count` / `request_count` * 100, 2)
        ELSE 0
    END
) STORED COMMENT '覆盖率',

`display_rate` FLOAT GENERATED ALWAYS AS (
    CASE 
        WHEN `match_count` > 0 
        THEN ROUND(`display_count` / `match_count` * 100, 2)
        ELSE 0
    END
) STORED COMMENT '展示率',

`click_rate` FLOAT GENERATED ALWAYS AS (
    CASE 
        WHEN `display_count` > 0 
        THEN ROUND(`click_count` / `display_count` * 100, 2)
        ELSE 0
    END
) STORED COMMENT '点击率'
```

**优势**:
- 自动计算，无需应用层计算
- 查询时直接使用，性能更好
- 数据一致性保证

## 八、去重机制

### 8.1 唯一性约束

**数据库层面**:
```sql
UNIQUE KEY `uq_ad_data_date_product` (`date`, `product_id`)
```

**作用**: 确保同一日期和产品只能有一条记录

### 8.2 去重逻辑

#### TQT API导入
```python
# 1. 查询数据库中是否已存在
existing_query = select(AdData).where(
    AdData.product_id == product_id,
    func.date(AdData.date) == func.date(item_date)
)
existing = await db.execute(existing_query)
existing_record = existing.scalar_one_or_none()

# 2. 如果存在，更新；如果不存在，插入
if existing_record:
    # 更新现有记录
    existing_record.request_count = request_count
    # ... 更新其他字段
    updated_count += 1
else:
    # 插入新记录
    new_record = AdData(...)
    db.add(new_record)
    inserted_count += 1
```

#### Excel导入
```python
# 1. 批量预查询已存在的记录
date_product_pairs = set()
for row in df:
    date_product_pairs.add((date, product_id))

existing_records = {}
if date_product_pairs:
    # 批量查询
    conditions = [and_(
        func.date(AdData.date) == func.date(d),
        AdData.product_id == p
    ) for d, p in date_product_pairs]
    query = select(AdData).where(or_(*conditions))
    results = await db.execute(query)
    for record in results.scalars():
        key = (func.date(record.date), record.product_id)
        existing_records[key] = record

# 2. 处理每条数据时检查
key = (data_date, product_id)
if key in existing_records:
    # 更新
    existing_records[key].request_count = request_count
    # ...
else:
    # 插入
    new_record = AdData(...)
    db.add(new_record)
```

### 8.3 Excel内部去重

**逻辑**: Excel文件内部可能包含重复数据（相同日期和产品）

**处理方式**:
- 按`(date, product_name)`分组
- 如果有多行，只保留最后一行
- 跳过前面的重复行

**实现**:
```python
excel_duplicate_map = {}
for index, row in df.iterrows():
    key = (row['date'], row['product_name'])
    if key not in excel_duplicate_map:
        excel_duplicate_map[key] = []
    excel_duplicate_map[key].append(index + 2)  # Excel行号（从2开始）

# 只保留每组的最后一行
rows_to_skip = set()
for key, rows in excel_duplicate_map.items():
    if len(rows) > 1:
        rows_to_skip.update(rows[:-1])  # 跳过除最后一行外的所有行
```

## 九、减扣计算

### 9.1 减扣比例

每个产品都有两个减扣比例：
- **ecpm_deduct_ratio**: eCPM减扣比例（0.0-1.0）
- **revenue_deduct_ratio**: 收益减扣比例（0.0-1.0）

### 9.2 计算公式

#### eCPM减扣
```
ecpm_after_deduct = ecpm_before_deduct × (1 - ecpm_deduct_ratio)
```

#### 收益减扣
```
revenue_after_deduct = revenue_before_deduct × (1 - revenue_deduct_ratio)
```

### 9.3 实现逻辑

**TQT API导入**:
```python
# 获取产品信息
product = await find_or_create_product(...)

# 计算减扣后的值
ecpm_deduct_ratio = product.ecpm_deduct_ratio or 0.0
revenue_deduct_ratio = product.revenue_deduct_ratio or 0.0

ecpm_after_deduct = ecpm_before_deduct * (1 - ecpm_deduct_ratio)
revenue_after_deduct = revenue_before_deduct * (1 - revenue_deduct_ratio)
```

**Excel导入**:
```python
# 如果Excel中提供了减扣后的值，直接使用
# 否则根据产品的减扣比例计算
if 'ecpm_after_deduct' in row:
    ecpm_after_deduct = parse_float(row['ecpm_after_deduct'])
else:
    ecpm_after_deduct = ecpm_before_deduct * (1 - product.ecpm_deduct_ratio)
```

## 十、产品分配历史

### 10.1 背景

产品可能在不同客户间转移。为了确保历史数据的归属正确，系统使用`product_assignments`表记录产品的分配历史。

### 10.2 表结构

```sql
CREATE TABLE `product_assignments` (
    `id` INT PRIMARY KEY AUTO_INCREMENT,
    `product_id` INT NOT NULL,
    `client_id` INT NOT NULL,
    `start_date` DATE NOT NULL,
    `end_date` DATE NULL,
    `created_at` DATETIME(6) DEFAULT CURRENT_TIMESTAMP(6)
);
```

### 10.3 匹配逻辑

**查询时匹配**:
```python
# 根据广告数据的日期匹配正确的分配记录
query = query.join(
    ProductAssignment,
    and_(
        ProductAssignment.product_id == Product.id,
        func.date(AdData.date) >= ProductAssignment.start_date,
        or_(
            ProductAssignment.end_date.is_(None),  # 未结束的分配
            func.date(AdData.date) <= ProductAssignment.end_date  # 已结束的分配
        )
    )
)
query = query.join(Client, ProductAssignment.client_id == Client.id)
```

**逻辑说明**:
- 如果数据日期在分配记录的`start_date`和`end_date`之间，数据属于该客户
- 如果`end_date`为NULL，表示当前分配，数据属于该客户
- 确保历史数据归属正确

```javascript
async function fetchFilterProducts(clientId) {

    let startDate = null;
    let endDate = null;
    if (searchForm.dateRange && searchForm.dateRange.length === 2) {
        startDate = searchForm.dateRange[0];
        endDate = searchForm.dateRange[1];
    }
    // 如果没有选择日期范围，后端默认使用本月数据
    
    // 2. 调用API获取产品列表
    const result = await getProductsWithData(clientId || null, startDate, endDate);
    
    // 3. 转换数据格式并排序
    const productOptions = result.data
        .filter(item => item && item.id != null)
        .map(item => ({
            label: item.name || '未知产品',
            value: String(item.id)
        }))
        .sort((a, b) => {
            // 按产品名称排序（中文和英文混合排序）
            return a.label.localeCompare(b.label, 'zh-CN', { numeric: true });
        });
    
    // 4. 添加"全部产品"选项
    filterProducts.value = [
        { label: '全部产品', value: '' },
        ...productOptions
    ];
}
```

## 十三、关键设计决策

### 13.1 为什么使用DateTime而不是Date？

**原因**:
- 数据库中的`date`字段是`DATETIME`类型
- 支持更精确的时间查询
- 兼容性更好

**处理**:
- 存储时使用`00:00:00`（当天开始时间）
- 查询时使用日期范围（`>= start_date 00:00:00 AND <= end_date 23:59:59`）

### 13.2 为什么默认显示本月数据？

**原因**:
- 提高用户体验，用户最关心最近的数据
- 减少初始查询的数据量，提高性能
- 符合业务需求

**实现**:
- 前端不传日期范围时，后端自动使用当前月
- 前端提示："默认查询数据是本月数据"

### 13.3 为什么产品列表要动态更新？

**原因**:
- 不同日期范围内可能有不同的产品
- 不同客户有不同的产品
- 确保用户只能选择有效的数据

**实现**:
- 客户变化时更新产品列表
- 日期范围变化时更新产品列表
- 产品列表按名称排序，便于查找

### 13.4 为什么使用产品分配历史表？

**原因**:
- 产品可能在不同客户间转移
- 需要确保历史数据的归属正确
- 支持产品归属的时间段管理

**实现**:
- 查询时根据数据日期匹配正确的分配记录
- 兼容旧的查询方式（直接通过Product.client_id）

## 十五、错误处理

### 15.1 数据验证错误

- **日期格式错误**: 跳过该条数据，记录警告
- **产品名称为空**: 跳过该条数据，记录警告
- **数值字段错误**: 使用默认值0，记录警告

### 15.2 数据库错误

- **唯一性约束冲突**: 更新现有记录而不是插入
- **外键约束错误**: 记录错误，跳过该条数据
- **事务回滚**: 发生错误时回滚事务，保证数据一致性

### 15.3 API错误

- **TQT API错误**: 记录错误日志，不中断任务
- **网络超时**: 重试机制（如果配置）
- **响应格式错误**: 记录错误，跳过本次任务
