# TQT定时任务工作逻辑详细说明

## 一、任务概述

**任务名称**: `tqt_api_task`  
**功能**: 从TQT API获取广告数据，经过验证、去重、计算后导入到数据库  
**执行频率**: 定时执行（通常每5分钟）  
**数据来源**: TQT API (`https://union.e-kivi.com/open/api/report/data`)  
**数据目标**: 数据库 `ad_data` 表

---

## 二、整体工作流程

```
开始
  ↓
1. 准备API请求参数（查询昨天的数据）
  ↓
2. 生成API签名
  ↓
3. 调用TQT API获取数据
  ↓
4. 解析API响应
  ↓
5. 初始化数据库会话和管理员客户
  ↓
6. 遍历每条数据（循环处理）
  ├─ 步骤1: 提取基础字段
  ├─ 步骤2: 验证日期格式
  ├─ 步骤3: 验证产品名称
  ├─ 步骤4: 查找/创建产品
  ├─ 步骤5: 解析数值字段
  ├─ 步骤6.1: 计算eCPM
  ├─ 步骤5.2: 计算减扣后的值
  ├─ 步骤6: 检查数据是否重复
  └─ 步骤7: 新建或更新数据
  ↓
7. 提交事务
  ↓
8. 记录统计信息
  ↓
结束
```

## 三、详细步骤说明

### 阶段一：API请求准备（第1-3步）

#### 1. 构建请求参数
- **目的**: 准备调用TQT API所需的参数
- **关键参数**:
  - `appKey`: 应用密钥 (`07ycrvnf`)
  - `startDate`: 开始日期（昨天的日期，格式：`YYYY-MM-DD`）
  - `endDate`: 结束日期（昨天的日期，格式：`YYYY-MM-DD`）
  - `page`: 页码（从1开始）
  - `pageSize`: 每页数据量（100条）
  - `type`: 数据类型（`all` 表示全部）

**注意**: 任务查询的是**昨天的数据**，不是当天的数据。

#### 2. 生成API签名
- **函数**: `generate_sign()`
- **签名规则**（TQT API要求）:
  1. 按参数名ASCII升序排序（排除`sign`参数）
  2. 将所有参数拼接成 `key + value` 的字符串（无分隔符）
  3. 在首尾拼接 `apiSecret`
  4. 将整个字符串转为小写
  5. 进行MD5加密，结果转为小写十六进制字符串

**示例**:
```
参数: {appKey: "07ycrvnf", startDate: "2024-01-01", endDate: "2024-01-01"}
排序后: appKey07ycrvnfendDate2024-01-01startDate2024-01-01
拼接secret: secret + 参数字符串 + secret
MD5加密: 得到32位小写十六进制字符串
```

#### 3. 调用TQT API
- **方法**: POST请求
- **URL**: `https://union.e-kivi.com/open/api/report/data`
- **超时**: 20秒
- **响应格式**: JSON
  - `code`: 状态码（200表示成功）
  - `list`: 数据列表（数组）
  - `message`: 错误信息（如果失败）

---

### 阶段二：数据库初始化（第4-5步）

#### 4. 创建数据库会话
- **目的**: 所有数据库操作在同一个事务中执行
- **好处**: 
  - 确保数据一致性
  - 如果出错可以回滚
  - 提高性能（批量提交）

#### 5. 获取或创建管理员的客户
- **目的**: 为后续创建新产品做准备
- **查找策略**（优先级从高到低）:
  1. 优先查找 `username = 'admin'` 的管理员用户
  2. 如果没有，查找任意一个管理员用户
  3. 查找该管理员的客户（优先查找"默认客户（导入数据）"）
  4. 如果没有，查找管理员的任意客户
  5. 如果管理员没有任何客户，自动创建"默认客户（导入数据）"

**结果**: 获得 `admin_client_id`，用于后续创建新产品时关联

---

### 阶段三：数据处理循环（第6步，对每条数据执行）

对API返回的每条数据，执行以下步骤：

#### 步骤1：提取和验证基础字段

**提取字段**:
- `date`: 日期字符串（格式：`YYYY-MM-DD`）
- `url`: 产品名称/标识（TQT API使用此字段存储产品名称）

**验证**:
- 检查字段是否存在
- 检查是否为空字符串

---

#### 步骤2：验证并解析日期

**验证内容**:
1. 检查日期字符串是否为空
2. 检查日期格式是否为 `YYYY-MM-DD`
3. 尝试解析为 `datetime` 对象

**时区处理**:
- 将本地时区的 `datetime` 转换为UTC时区
- 原因：数据库统一使用UTC时区存储

**错误处理**:
- 如果日期为空或格式错误，记录警告并跳过该条数据

---

#### 步骤3：验证产品名称

**验证内容**:
- 检查产品名称是否为空
- 去除首尾空格

**错误处理**:
- 如果产品名称为空，记录警告并跳过该条数据

---

#### 步骤4：查找或创建产品

**查找产品**:
- 根据产品名称在数据库中查找对应的产品记录
- SQL查询: `SELECT * FROM products WHERE name = ?`

**如果找到产品**:
- 继续后续步骤

**如果找不到产品**:
1. 检查是否有 `admin_client_id`（管理员客户ID）
2. 如果没有，记录警告并跳过该条数据
3. 如果有，创建新产品:
   - `client_id`: 关联到管理员客户
   - `name`: 产品名称
   - `ecpm_deduct_ratio`: 0.0（默认不扣减）
   - `revenue_deduct_ratio`: 0.0（默认不扣减）
   - `is_active`: True
4. 刷新对象以获取产品ID

**创建产品的优先级**:
1. 优先匹配给 `username = 'admin'` 的管理员
2. 如果没有admin，匹配给任意一个管理员
3. 如果管理员没有客户，自动创建"默认客户（导入数据）"

---

#### 步骤5：解析数值字段

**提取并转换的字段**:
- `requests` → `item_request_count` (int): 请求数
- `matche_que` → `item_match_count` (int): 匹配数（注意：API字段名可能是拼写错误）
- `adimpressions` → `item_display_count` (int): 展示数（曝光数）
- `clicks` → `item_click_count` (int): 点击数
- `revenue` → `item_revenue` (float): 收益

**错误处理**:
- 如果数值字段格式错误（无法转换为整数或浮点数），记录警告并跳过该条数据

---

#### 步骤6.1：计算eCPM

**计算公式**:
```
eCPM = (收益 / 展示数) × 1000
```

**特殊情况**:
- 如果展示数为0，则eCPM为0（避免除零错误）

**说明**:
- eCPM（Effective Cost Per Mille）表示每千次展示的有效成本
- 用于衡量广告效果和收益

---

#### 步骤5.2：按照匹配的客户查找对应的扣减比例

**获取减扣比例**:
- `ecpm_deduct_ratio`: eCPM减扣比例（0.0-1.0）
- `revenue_deduct_ratio`: 收益减扣比例（0.0-1.0）

**来源**: 从产品记录中获取（产品关联到客户，客户可能有不同的减扣比例）

**计算减扣后的值**:
```
减扣后eCPM = 原始eCPM × (1 - ecpm_deduct_ratio)
减扣后收益 = 原始收益 × (1 - revenue_deduct_ratio)
```

**示例**:
- 如果减扣比例为0.1（10%），则减扣后值 = 原始值 × 0.9
- 如果减扣比例为0.2（20%），则减扣后值 = 原始值 × 0.8

---

#### 步骤6：检查数据是否重复

**查询条件**:
- `date` = 当前数据的日期
- `product_id` = 当前产品的ID

**SQL查询**:
```sql
SELECT * FROM ad_data 
WHERE date = ? AND product_id = ?
```

**结果**:
- 如果找到记录：`existing_data` 不为空
- 如果没找到：`existing_data` 为 `None`

---

#### 步骤7：处理数据（新建或更新）

##### 情况A：数据已存在（`existing_data` 不为空）

**比较所有字段**，检查是否有变化：

1. **基础数据字段**:
   - `request_count`: 请求数
   - `match_count`: 匹配数
   - `display_count`: 展示数
   - `click_count`: 点击数

2. **减扣前的值**:
   - `ecpm_before_deduct`: eCPM（减扣前）
   - `revenue_before_deduct`: 收益（减扣前）

3. **减扣后的值**:
   - `ecpm_after_deduct`: eCPM（减扣后）
   - `revenue_after_deduct`: 收益（减扣后）

**比较规则**:
- 整数字段：直接比较是否相等
- 浮点数字段：允许0.01的误差（`abs(旧值 - 新值) > 0.01`）

**更新逻辑**:
- 如果**有变化**:
  - 更新所有变化的字段
  - 记录变化字段的详细信息
  - `updated_count += 1`
  - 记录日志：`更新广告数据: 日期=xxx, 产品=xxx, 变化字段: ...`

- 如果**完全相同**:
  - 跳过该条数据
  - `skipped_count += 1`
  - 记录日志：`数据完全相同，跳过: 日期=xxx, 产品=xxx`

**重要说明**:
- 即使减扣比例改变了，算出来的减扣后值不一样也会更新
- 这确保了当产品的减扣比例被修改后，历史数据也会重新计算

##### 情况B：数据不存在（`existing_data` 为 `None`）

**创建新记录**:
- 创建 `AdData` 对象，包含所有字段：
  - `date`: 数据日期（UTC时区）
  - `product_id`: 关联的产品ID
  - `request_count`: 请求数
  - `match_count`: 匹配数
  - `display_count`: 展示数
  - `click_count`: 点击数
  - `ecpm_before_deduct`: 减扣前的eCPM
  - `ecpm_after_deduct`: 减扣后的eCPM
  - `revenue_before_deduct`: 减扣前的收益
  - `revenue_after_deduct`: 减扣后的收益

- 添加到数据库会话（暂未提交）
- `inserted_count += 1`
- 记录日志：`添加广告数据: 日期=xxx, 产品=xxx, ...`

---

### 阶段四：提交和统计（第7-8步）

#### 7. 提交事务

**时机**: 所有数据都处理完成后

**操作**:
- `await db.commit()`: 一次性提交所有更改到数据库

**好处**:
- 提高性能（批量提交比逐条提交快）
- 确保数据一致性（要么全部成功，要么全部失败）
- 如果出错可以回滚整个事务

#### 8. 记录统计信息

**统计指标**:
- `inserted_count`: 成功插入的数据条数
- `updated_count`: 成功更新的数据条数
- `skipped_count`: 跳过重复的数据条数
- `error_count`: 处理出错的数据条数

**日志输出**:
```
数据导入完成: 成功插入 X 条, 成功更新 Y 条, 跳过重复 Z 条, 错误 W 条
```

## 四、错误处理机制

### 单条数据错误处理

**捕获范围**: 每条数据的处理过程

**处理方式**:
- 使用 `try-except` 捕获异常
- 记录详细错误信息（包括堆栈跟踪）
- `error_count += 1`
- `continue`: 继续处理下一条数据，不中断整个流程

**错误类型**:
- 日期格式错误
- 产品名称为空
- 数值字段格式错误
- 数据库操作错误
- 其他未预期的错误

### 全局错误处理

**捕获范围**: 整个任务执行过程

**处理方式**:
- 记录详细错误信息
- 重新抛出异常，让定时任务调度器记录错误状态
- 定时任务调度器的锁机制会自动释放
- 错误信息会保存到数据库

## 六、关键设计决策

### 1. 为什么查询昨天的数据？
- 通常当天的数据可能还不完整
- 昨天的数据已经完整，可以准确统计

### 2. 为什么先解析数据再检查重复？
- 需要先计算减扣后的值，才能准确比较
- 如果减扣比例改变了，减扣后的值也会改变，需要更新

### 3. 为什么允许0.01的误差？
- 浮点数计算可能存在精度问题
- 避免因微小的精度差异导致不必要的更新

### 4. 为什么使用事务？
- 确保数据一致性
- 提高性能（批量提交）
- 如果出错可以回滚

### 5. 为什么单条数据出错不影响其他数据？
- 提高容错性
- 即使部分数据有问题，其他数据仍能正常导入

## 七、性能优化

1. **批量提交**: 所有数据处理完成后一次性提交，而不是逐条提交
2. **索引优化**: 数据库表有索引优化查询性能：
   - `idx_ad_data_date`: 日期索引
   - `idx_ad_data_product`: 产品ID索引
   - `idx_ad_data_date_product`: 日期+产品ID复合索引
3. **异步处理**: 使用异步函数和异步数据库操作，提高并发性能

## 八、日志记录

### 日志级别

- **INFO**: 正常操作信息（数据添加、更新、跳过）
- **WARNING**: 警告信息（数据验证失败、跳过数据）
- **ERROR**: 错误信息（异常、API错误）

### 关键日志点

1. 任务开始执行
2. 创建新产品
3. 添加广告数据
4. 更新广告数据
5. 数据完全相同，跳过
6. 数据验证失败
7. 处理数据出错
8. 数据导入完成统计

## 九、数据模型关系

```
User (用户)
  ↓ (一对多)
Client (客户)
  ↓ (一对多)
Product (产品)
  ↓ (一对多)
AdData (广告数据)
```

**说明**:
- 一个用户可以有多个客户
- 一个客户可以有多个产品
- 一个产品可以有多个广告数据记录（按日期区分）

## 十、注意事项

1. **时区处理**: 所有日期都转换为UTC时区存储
2. **数据唯一性**: 通过 `(date, product_id)` 唯一约束确保数据不重复
3. **减扣比例**: 如果产品的减扣比例被修改，历史数据不会自动更新，但新导入的数据会使用新的减扣比例
4. **API限制**: 注意API的调用频率限制和超时设置
5. **数据完整性**: 如果API返回的数据不完整，会跳过该条数据并记录错误
